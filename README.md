Консольное приложение учёта парка «ВышКат» 

## Логика решения
Приложение «ВышКат» предназначено для учёта транспорта и инвентаря парка. Пользователь взаимодействует с программой через консольное меню, с помощью которого может добавлять транспортные средства и инвентарные предметы, а также формировать отчёты.

Каждый объект имеет название и уникальный инвентарный номер. Для транспорта дополнительно хранится оценка удобства для новичков от 1 до 10, а для устройств, потребляющих энергию — суточное потребление энергии в кВт·ч. Транспорт перед добавлением в парк проходит технический осмотр через ServiceCenter. Если проверка не пройдена, объект не добавляется.

Данные хранятся в оперативной памяти в InMemoryStorage, который обеспечивает уникальность инвентарных номеров и предоставляет методы для получения объектов. Сервис отчётов использует хранилище для подсчёта транспорта, расчёта суммарного суточного потребления энергии, определения транспорта, подходящего новичкам (оценка от 6), и вывода полного списка инвентаря.

Интерфейсы

Для разделения ответственности и уменьшения связанности компонентов используются следующие интерфейсы:

- InventoryItem — описывает общий контракт инвентарного объекта: название и инвентарный номер. Позволяет работать с разными типами объектов единообразно.
- Transport — расширяет InventoryItem и описывает транспорт, предоставляя оценку удобства для новичков.
- EnergyConsumer — описывает объекты, имеющие суточное потребление энергии. Благодаря этому отчёт рассчитывает расход без привязки к конкретным типам энергоустройств.
- Storage — определяет операции хранения, получения и поиска объектов. Сервисы зависят от интерфейса, а не от конкретной реализации хранилища.
- ServiceCenter — определяет операцию технического осмотра транспорта. Позволяет использовать разные реализации проверки, в том числе тестовую.
- Runner — определяет точку запуска приложения через метод Run(), не привязывая main к конкретной реализации консольного интерфейса.

Программа состоит из следующих частей:
 - Domain — модели предметной области, интерфейсы и проверка корректности данных.
 - Repository — хранение и поиск объектов.
 - Service — бизнес-логика добавления объектов и формирования отчётов.
 - UI — консольное меню и взаимодействие с пользователем.
 - App — ручной DI-контейнер, который создаёт компоненты и связывает их зависимости. Используется, так как это явно требуется в задании, хотя можно было вместо этого прописать все в main.

Зависимости передаются через конструкторы. ParkService работает с интерфейсами хранилища и технического центра, поэтому в тестах можно подменить ServiceCenter на тестовую реализацию и проверить поведение приложения без реального технического осмотра.

## Запуск приложения
Для запуска необходимо перейти в корневую директорию проекта и выполнить команду:

```bash
go run .
```

После запуска отображается консольное меню. Пользователь выбирает нужный пункт, вводя его номер.

**Пример работы**

```text
=== ВышКат ===
1. Добавить транспорт
2. Добавить инвентарный предмет
3. Показать весь транспорт и инвентарь
4. Показать суточный расход энергии
5. Показать транспорт для новичков
6. Показать количество транспорта и инвентаря
0. Выход

Выберите действие: 1
```

При добавлении транспорта пользователь указывает его тип, название, инвентарный номер и оценку удобства для новичков. Для электрического транспорта дополнительно вводится суточное потребление энергии. Перед добавлением транспорт проходит технический осмотр.

При добавлении инвентаря можно выбрать шлем, зарядную станцию или док-станцию и ввести необходимые характеристики.

## Вывод отчётов

Приложение позволяет:
- вывести список всех транспортных средств и инвентарных предметов с названиями и инвентарными номерами;
- узнать суммарное суточное потребление энергии в кВт·ч;
- получить список транспорта для новичков;
- посмотреть количество транспортных средств и остальных инвентарных предметов.

Если введены некорректные данные, используется обработка ошибок с выводом сообщения пользователю. При попытке добавить транспорт, не прошедший технический осмотр, или объект с уже существующим инвентарным номером добавление отклоняется.

Для завершения работы необходимо выбрать пункт `0. Выход`.

## Использованные принципы SOLID
Наиболее явно применен Single Responsibility Principle — принцип единственной ответственности:

- internal/domain/ — описывает модели транспорта и инвентаря, их свойства и валидацию.
- internal/repository/inventory_storage.go — отвечает за хранение объектов.
- internal/service/park.go — отвечает за добавление объектов в парк и проверку техосмотра.
- internal/service/reports.go — формирует отчёты.
- internal/ui/console.go — отвечает за взаимодействие с пользователем.
- internal/app/container.go — собирает зависимости приложения.
У каждого модуля своя основная ответственность. 

Также применен принцип DIP — принцип инверсии зависимостей:
В internal/service/park.go ParkService зависит от интерфейсов ServiceCenter и repository.Storage, а не от конкретных реализаций. 

```
type ParkService struct {
	repository    repository.Storage
	serviceCenter ServiceCenter
}
```

Благодаря чему можно подменять логику техосмотра и способ хранения данных, не изменяя при этом ParkService.

Принцип разделения интерфейсов ISP также использован в коде. Вместо одного большого интерфейса используются маленькие:

```
type InventoryItem interface {
    Name() string
    InventoryNumber() string
}
```

```
type Transport interface {
    InventoryItem
    EaseOfUse() int
}
```

```
type EnergyConsumer interface {
    DailyEnergyConsumption() float64
}
```

Благодаря этому типы реализуют только те контракты, которые им действительно нужны. Например, шлему не требуется реализовывать DailyEnergyConsumption(), поскольку он не потребляет энергию в рамках модели. А отчёт расхода энергии может работать с любым объектом, реализующим EnergyConsumer.

## Принцип который "почти нарушен"
Принцип который "почти нарушен" - OCP (Open/Closed Principle) — принцип открытости/закрытости. Он соблюдается не полностью, так как при добавлении нового вида транспорта, потребуется изменить internal/ui/console.go: добавить новый вариант в switch внутри addTransport().

Однако, учитывая, что вывод в консоль используется просто для демонстрации работы приложения, я посчитала что реализации фабрики или системы регистрации типов избыточна для текущего задания.

## Добавление новых элементов

Интерфейсы в internal/domain/interfaces.go позволяют работать с разными видами транспорта единообразно. То есть добавление нового транспорта не приведет к необходимости менять логику работы парка. Аналогично добавление нового инвентаря не потребует изменений в функциях работы с парком. Как уже было сказано выше, единственное что потребует изменений это функции взаимодействия с консолью. 

Сейчас программа не реализует учет сотрудников, поэтому для них придется создавать отдельные интерфейсы и функции работы с ними, так как текущая реализация поддерживает работу только с инвентарными объектами. Добавление склада запчастей также потребует нового интерфейса и функций, если только запчасти не будут считаться инвентарными объектами. 

## Подмена зависимостей в тестах

В internal/service/service_center.go объявлен интерфейс:

```
type ServiceCenter interface {
	Accept(transport domain.Transport) bool
}
```

ParkService принимает его через конструктор в internal/service/park.go:

```
func NewParkService(
	repo repository.Storage,
	serviceCenter ServiceCenter,
) *ParkService {
	return &ParkService{
		repository:    repo,
		serviceCenter: serviceCenter,
	}
}
```

В тестах используется подмена зависимости - создается фейковый сервисный центр, реализующий необходимый интерфейс:

```
type fakeServiceCenter struct {
	accepted bool
	calls    int
}
```

```
func (f *fakeServiceCenter) Accept(transport domain.Transport) bool {
	f.calls++
	return f.accepted
}
```

В тесте TestParkService_AddTransport сначала проверяется добавление транспорта после успешного техосмотра, поэтому 	center := &fakeServiceCenter{accepted: true} используется сервисный центр, который всегда возвращает true, затем проверяется, что не добавляются транспортные средства, которые не прошли техосмотр, поэтому используется 
center := &fakeServiceCenter{accepted: false}, который отвергает весь транспорт.
